# Karmik — Memory System

## Overview

Karmik uses three memory tiers that operate simultaneously. Each tier has a different
time horizon, retrieval mechanism, and storage backend.

```
┌──────────────────────────────────────────────────────┐
│  Tier 1: Ephemeral (Context Window)                  │
│  Scope: current session only                         │
│  Storage: in-process Dart list                       │
│  Retrieval: sequential (all messages in context)     │
│  Cleared: on session end                             │
└──────────────────────────────────────────────────────┘
                        │
                        ▼ persisted at session end
┌──────────────────────────────────────────────────────┐
│  Tier 2: Persistent History                          │
│  Scope: per-agent, indefinite (configurable TTL)     │
│  Storage: SQLite (encrypted)                         │
│  Retrieval: most-recent N turns loaded into context  │
│  Cleared: per retention policy                       │
└──────────────────────────────────────────────────────┘
                        │
                        ▼ summarized and embedded
┌──────────────────────────────────────────────────────┐
│  Tier 3: Long-term Semantic Memory                   │
│  Scope: per-agent or shared (user-configured)        │
│  Storage: sqlite-vec (vector extension on SQLite)    │
│  Retrieval: semantic similarity search at session start│
│  Cleared: never (unless user manually deletes)       │
└──────────────────────────────────────────────────────┘
```

## Tier 1: Ephemeral Memory

The active context window for the current inference session. Managed by the agent executor.

- All messages (system, user, assistant, tool results) are held in a `List<Message>` in memory
- If the conversation exceeds the model's context limit, older messages are summarized and
  compressed (rolling summary) to make room
- On session end: the full conversation is written to Tier 2 (if persistent history enabled)
- On app kill: ephemeral memory is lost (by design; Tier 2 was already written)

**Rolling context compression** (when context window fills):
```
[system_prompt] [memory_injection] [summarized_older_turns] [recent_N_turns] [current_turn]
```
The summarized block is generated by a fast model call and replaces the oldest N messages.

## Tier 2: Persistent History

Full conversation log stored in SQLite. Loaded partially into context at session start.

### Schema

```sql
CREATE TABLE conversations (
  id          TEXT PRIMARY KEY,
  agent_id    TEXT NOT NULL,
  created_at  INTEGER NOT NULL,   -- unix timestamp
  updated_at  INTEGER NOT NULL,
  title       TEXT,               -- auto-generated or user-set
  model_id    TEXT NOT NULL,
  FOREIGN KEY (agent_id) REFERENCES agents(id)
);

CREATE TABLE messages (
  id              TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,
  role            TEXT NOT NULL,  -- "user" | "assistant" | "tool" | "system"
  content         TEXT NOT NULL,  -- JSON (supports multi-modal: text + image)
  tool_calls      TEXT,           -- JSON array, nullable
  tool_call_id    TEXT,           -- for tool result messages
  created_at      INTEGER NOT NULL,
  FOREIGN KEY (conversation_id) REFERENCES conversations(id)
);

CREATE INDEX idx_messages_conv ON messages(conversation_id, created_at);
CREATE INDEX idx_conversations_agent ON conversations(agent_id, updated_at);
```

### Context Loading Strategy

At session start, load the most-recent turns up to a configurable token budget
(default: 25% of the model's context window). Older turns are not loaded but remain
searchable via Tier 3.

```dart
Future<List<Message>> loadContextHistory(String conversationId, int tokenBudget) async {
  // Load messages newest-first until token budget is reached
  // Return in chronological order for context injection
}
```

### Retention Policy

Configured per agent in `MemoryConfig.historyRetentionDays`:
- `-1`: keep forever
- `30`: delete conversations older than 30 days
- `0`: ephemeral only (don't persist to Tier 2)

A background cleanup job runs weekly to purge expired conversations.

## Tier 3: Long-term Semantic Memory

Vector-indexed memories that persist indefinitely. Used for facts, preferences, and summaries
that the agent should remember across sessions even when they fall out of the context window.

### Storage: sqlite-vec

`sqlite-vec` is a SQLite extension that adds vector similarity search. Chosen because:
- No separate process or service (same SQLite database)
- Runs entirely on-device
- Supports cosine similarity and L2 distance
- Compatible with ARM64 Android

```sql
-- Enable sqlite-vec extension
SELECT load_extension('libsqlite_vec.so');

CREATE TABLE memories (
  id          TEXT PRIMARY KEY,
  agent_id    TEXT NOT NULL,
  content     TEXT NOT NULL,       -- original text
  tags        TEXT,                -- JSON array of tags
  created_at  INTEGER NOT NULL,
  FOREIGN KEY (agent_id) REFERENCES agents(id)
);

-- Vector table (parallel to memories)
CREATE VIRTUAL TABLE memory_vectors USING vec0(
  memory_id   TEXT,
  embedding   float[384]           -- 384-dim for all-MiniLM-L6-v2
);
```

### Embedding Model

On-device embedding generation using **all-MiniLM-L6-v2** (ONNX format):
- 384-dimensional embeddings
- ~23MB model size
- ~50ms per embedding on mid-range Android
- No internet required

The embedding model is downloaded separately from chat models and is always available
once downloaded (not per-chat swappable).

### Memory Operations

**Storing a memory** (via `memory.store` tool or automatic summarization):
```dart
Future<String> storeMemory(String agentId, String content, List<String> tags) async {
  final id = generateUuid();
  final embedding = await embeddingModel.embed(content);
  await db.execute('INSERT INTO memories VALUES (?, ?, ?, ?, ?)', [...]);
  await db.execute('INSERT INTO memory_vectors VALUES (?, ?)', [id, embedding]);
  return id;
}
```

**Retrieving relevant memories** (at session start):
```dart
Future<List<Memory>> searchMemories(String agentId, String query, int limit) async {
  final queryEmbedding = await embeddingModel.embed(query);
  return await db.query('''
    SELECT m.content, m.tags, v.distance
    FROM memory_vectors v
    JOIN memories m ON m.id = v.memory_id
    WHERE m.agent_id = ?
      AND v.embedding MATCH ?
      AND k = ?
    ORDER BY v.distance
  ''', [agentId, queryEmbedding, limit]);
}
```

### Automatic Memory Formation

At conversation end (or at intervals for long sessions), a background process:
1. Generates a summary of the conversation (using a fast model call)
2. Extracts key facts and preferences ("user prefers morning meetings", "project deadline is July 15")
3. Embeds and stores each extracted item as a separate memory
4. Tags memories with conversation ID for traceability

This runs asynchronously and does not block the UI.

### Memory Scoping

```dart
enum MemoryScope {
  isolated,   // agent reads and writes only its own memories
  shared,     // agent can read from a shared pool across all agents
}
```

Shared memories are stored in an `agent_id = "__shared__"` partition. Agents must explicitly
declare `scope: shared` to read from or write to the shared pool.

## Memory Browser UI

Users can view, search, and delete their memories through the Memory Browser screen:
- List all memories for each agent (sorted by recency)
- Full-text search across memory content
- Delete individual memories or clear all memory for an agent
- Export memories as JSON (for backup)
- Privacy note: shows where each memory came from (conversation ID, date, source agent)

## Encryption

Both SQLite databases (conversation history and vector store) are encrypted using SQLCipher
with a key derived from the Android Keystore. The encryption key never leaves the device.
Backups via Android backup API are excluded for the encrypted databases.
